# Zibll OAuth2 接入开发文档

本文档定义了 Zibll OAuth2 代理服务的接口规范与安全建议。

## 1. 基础信息

- **Base URL**: `https://your-site.com/wp-json/zibll-oauth/v1`
- **认证模式**: 标准 OAuth2 Authorization Code Grant（支持 PKCE S256 与 OpenID Connect 1.0）
- **安全传输**: 必须使用 `HTTPS`

## 2. 术语与参数

| 字段 | 说明 |
| :--- | :--- |
| `client_id` | 应用唯一标识（在 Provider 后台创建应用获取） |
| `client_secret` | 应用密钥（请勿泄露，仅限服务端使用） |
| `redirect_uri` | 授权回调地址（必须与后台配置完全一致，精确匹配） |
| `code` | 临时授权码（有效期 10 分钟，SHA-256 存库，一次性原子消费） |
| `access_token` | 资源访问令牌（默认有效期 2 小时，SHA-256 存库） |
| `refresh_token` | 刷新令牌（有效期 180 天，SHA-256 存库，默认原子轮换与家族重放保护） |
| `id_token` | OIDC 身份令牌（请求包含 `openid` scope 时由 RS256 私钥签发） |
| `nonce` | OIDC 客户端防重放随机串（1–255 位可打印 ASCII 字符） |

---

## 3. 核心流程

### 3.1 授权 (Authorize)
引导用户在浏览器访问：
`GET /authorize`

**请求参数:**
- `response_type`: 固定为 `code`
- `client_id`: 应用标识
- `redirect_uri`: 回调地址
- `state`: 接入方生成的随机串（用于防 CSRF，回调时原样返回）
- `scope`: 权限范围（默认 `basic`，可选 `openid`, `basic`, `email`, `profile`, `phone`, `telegram`, `segments`，支持空格或逗号分隔）
- `nonce`: OIDC 防重放参数（推荐随 `scope=openid` 传入；仅允许 1–255 位可打印 ASCII 字符）
- `code_challenge`: PKCE 挑战值，推荐所有新接入应用使用
- `code_challenge_method`: 使用 PKCE 时必须显式传 `S256`；不接受 `plain`

接入方为每次授权生成独立的随机 `code_verifier`，长度 43–128 字符，字符集为 `A-Z a-z 0-9 - . _ ~`。将其保存在接入方服务端会话中，并计算 `code_challenge = BASE64URL(SHA256(code_verifier))`（不带 `=` 填充）。授权阶段只发送 challenge，换取令牌时再发送 verifier。S256 challenge 长度固定为 43 字符。

旧的服务端应用可暂时不传 PKCE 参数，仍须提供应用密钥。PKCE 不替代 `client_secret`。提供 challenge 后，服务端会强制验证 verifier；未提供 challenge 却在换取令牌时提交 verifier 的请求也会被拒绝。

**用户同意后回调:**
`{redirect_uri}?code={CODE}&state={STATE}`

> 财务授权（`/authorize_finance`）需要用户已完成一次应用授权（`/authorize`）。
> 若用户从未授权该应用，直接访问 `/authorize_finance` 将被拒绝。
> `/authorize_finance` 同样支持 PKCE，回调地址须精确匹配后台的财务回调地址。

### 3.2 换取令牌 (Token)
接入方后端通过 code 换取令牌：
`POST /token`

**请求参数:**
- `grant_type`: 固定为 `authorization_code`
- `client_id`: 应用标识 (可通过 POST body 或 `Authorization: Basic base64(client_id:client_secret)` 传递)
- `client_secret`: 应用密钥 (可通过 POST body 或 Basic Auth 传递)
- `code`: 回调获取的 code
- `redirect_uri`: 必须与授权时一致
- `code_verifier`: 使用 PKCE 时必须提供授权开始时保存在服务端会话中的原始 verifier

客户端认证可选择请求体参数或 Basic Auth，不能同时使用两种方式。Basic Auth 中的应用 ID 和密钥应先分别进行 `application/x-www-form-urlencoded` 编码，再以 `:` 连接并 base64 编码。认证失败返回 `401` 和 `WWW-Authenticate: Basic`。

授权码、访问令牌与刷新令牌均仅以 SHA-256 摘要保存在独立数据库表中，使用 UTC 时间记录有效期。授权码以原子条件更新标记消费，并发请求最多一个成功；正常登录与财务授权分别绑定各自回调地址、scope、state、nonce 和 PKCE 参数，确认表单被篡改时须重新授权。

**成功响应 (200 OK):**
```json
{
  "access_token": "AT_xxx",
  "token_type": "bearer",
  "expires_in": 7200,
  "refresh_token": "RT_xxx",
  "refresh_token_expires_in": 15552000,
  "scope": "openid basic email segments",
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6ImtfLi4uIn0..."
}
```
> 仅当本次授权的 `scope` 包含 `openid` 时返回 `id_token`。`id_token` 使用 RS256 签名，包含标准声明（`iss`、`sub`、`aud`、`exp`、`iat`、`auth_time`、`at_hash` 以及授权时提交的 `nonce`）和按 `scope` 裁剪的身份声明。

**错误响应（OAuth 字段兼容原 WordPress 错误格式）:**
```json
{
  "error": "invalid_grant",
  "error_description": "code 无效或已过期",
  "code": "invalid_grant",
  "message": "code 无效或已过期",
  "data": { "status": 400 }
}
```

### 3.3 刷新令牌 (Refresh)
当 access_token 快过期时，使用 refresh_token 获取新令牌：
`POST /token`

**请求参数:**
- `grant_type`: 固定为 `refresh_token`
- `client_id`: 应用标识
- `client_secret`: 应用密钥
- `refresh_token`: 当前的 refresh_token
- `rotate_refresh_token`: 可选，默认为轮换；仅当管理员在插件后台明确开启“允许旧版不轮换兼容模式”时传 `0` 才生效

**安全与兼容机制:**
1. **原子轮换**: 默认每次刷新均以数据库条件更新原子消费当前 `refresh_token`，签发新的 `access_token` 与同家族 `refresh_token`（若授权范围含 `openid` 也会签发新的 `id_token`）。并发刷新请求中最多仅一个能成功。
2. **家族重放检测**: 若同一条 `family_id` 会话链中已被使用或已被吊销的 `refresh_token` 再次提交，服务端会立即吊销整条家族下的全部 `access_token` 与 `refresh_token`，拒绝请求并记录审计日志。
3. **升级兼容**: 对于插件升级前已存在于 WordPress transient 的旧令牌，在有效期内首次校验或刷新时自动兼容并迁移纳入家族体系。

### 3.4 吊销令牌 (Revoke)
主动失效令牌（RFC 7009）：
`POST /revoke`

**请求参数:**
- `client_id`: 应用标识（或 Basic Auth）
- `client_secret`: 应用密钥（或 Basic Auth）
- `token`: 要吊销的令牌
- `token_type_hint`: 可选 `access_token` 或 `refresh_token`

**说明:** 吊销仅作用于归属当前调用应用的令牌；传入 `refresh_token` 时会同步吊销其关联 `family_id` 下的全部活跃访问令牌与刷新令牌。

**成功响应 (200 OK):**
```json
{
  "revoked": true
}
```

**错误响应（OAuth 字段兼容原 WordPress 错误格式）:**
```json
{
  "error": "invalid_client",
  "error_description": "client_secret 无效",
  "code": "invalid_client",
  "message": "client_secret 无效",
  "data": { "status": 401 }
}
```

### 3.5 OIDC 发现文档与公钥集合 (Discovery & JWKS)
- **Discovery 文档**: `GET /.well-known/openid-configuration`
  - 返回 `issuer`、`authorization_endpoint`、`token_endpoint`、`userinfo_endpoint`、`jwks_uri`、`revocation_endpoint`、`introspection_endpoint`、`scopes_supported`、`claims_supported` 等标准元数据。
- **JWKS 公钥**: `GET /jwks`
  - 返回 `{"keys": [{"kty": "RSA", "use": "sig", "alg": "RS256", "kid": "...", "n": "...", "e": "..."}]}`，供接入方离线验签 `id_token`；验签端必须强校验 `alg=RS256` 与 `exp`/`iss`/`aud`。
- **部署与 Nginx 注意事项**:
  - RS256 私钥由 `Zibll_Oauth_OIDC::provision_keys_file()` 写入站外受保护目录（`.xingxy-private/<site>/oauth-oidc-keys.php`，权限 `0640` 供 PHP-FPM 只读），也可通过环境变量/常量 `ZIBLL_OAUTH_OIDC_PRIVATE_KEY` 注入；未配置时不回退任何硬编码密钥。
  - 若站点使用宝塔/Nginx 默认规则 `location ~ \.well-known { allow all; }`，该正则会截胡 `/wp-json/zibll-oauth/v1/.well-known/openid-configuration` 导致返回 `HTTP 404`。必须在站点 Nginx 配置中添加精确匹配规则（或将证书规则锚定为 `location ^~ /.well-known/`）：
    ```nginx
    location = /wp-json/zibll-oauth/v1/.well-known/openid-configuration {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root/index.php;
        fastcgi_param SCRIPT_NAME /index.php;
        fastcgi_pass unix:/tmp/php-cgi-84.sock;
        fastcgi_intercept_errors off;
    }
    ```

### 3.6 令牌内省 (Introspect, RFC 7662)
供接入方后端或资源服务核验给定令牌的有效性：
`POST /introspect`

**请求参数:**
- `client_id`: 应用标识（或 Basic Auth）
- `client_secret`: 应用密钥（或 Basic Auth）
- `token`: 待核验的 `access_token` 或 `refresh_token`
- `token_type_hint`: 可选 `access_token` 或 `refresh_token`

**说明:** 为防止跨应用探针，非当前 `client_id` 签发的令牌、已吊销、已过期或用户已撤回授权的令牌统一返回 `200 {"active": false}`。

**有效响应示例 (200 OK):**
```json
{
  "active": true,
  "scope": "openid basic segments",
  "client_id": "zo_xxx",
  "sub": "o_xxx",
  "uid": 123,
  "token_type": "Bearer",
  "exp": 1794930000,
  "iat": 1794922800,
  "tg_uid": 700000000
}
```

## 5. 财务扣款 (异步模型)

本服务提供免密扣款能力，扣款过程为异步执行。

### 5.1 发起扣款 (Deduct)
`POST /finance/deduct`
Header: `Authorization: Bearer <access_token>`

**Body 参数:**
- `product_name`: 商品名称 (必填)
- `amount`: 金额 (必填，必须 > 0)
- `order_no`: 你的订单号 (必填，幂等键，全局唯一)

**响应状态码:**
- `202 Accepted`: 订单已受理，正在异步处理
- `200 OK`: 订单已处理完毕（通常见于幂等重试时）

**响应示例 (202 Accepted - 处理中):**
```json
{
  "trade_no": "zod_xxx",
  "order_no": "ORD123",
  "status": "processing",
  "message": "订单已受理，处理中",
  "amount": 10.00
}
```

**响应示例 (200 OK - 成功):**
```json
{
  "trade_no": "zod_xxx",
  "order_no": "ORD123",
  "status": "success",
  "message": "订单已处理完成",
  "amount": 10.00,
  "balance": 90.50
}
```

**响应示例 (200 OK - 失败):**
```json
{
  "trade_no": "zod_xxx",
  "order_no": "ORD123",
  "status": "failed",
  "message": "订单处理失败",
  "amount": 10.00
}
```

### 5.2 查询结果 (Verify)
`GET /finance/verify`
Header: `Authorization: Bearer <access_token>`

**参数:** `trade_no` 或 `order_no`（至少传一个）

**成功响应 (200 OK):**
```json
{
  "trade_no": "zod_xxx",
  "order_no": "ORD123",
  "product_name": "商品名称",
  "amount": 10.00,
  "status": "success",
  "error_msg": "",
  "created_at": "2024-01-01 10:00:00",
  "updated_at": "2024-01-01 10:00:05"
}
```

**status 字段说明:**
- `processing`: 处理中
- `success`: 成功
- `failed`: 失败
- `unknown`: 未知

### 5.3 获取签约状态 (Sign Status)
`GET /finance/sign_status`
Header: `Authorization: Bearer <access_token>`

**成功响应 (200 OK):**
```json
{
  "openid": "o_xxx",
  "is_signed": true,
  "scope": "basic email",
  "finance_scope": 1,
  "status": 1,
  "created_at": "2024-01-01 10:00:00",
  "authorized_at": "2024-01-02 15:30:00"
}
```

**字段说明:**
- `openid`: 用户 OpenID
- `is_signed`: 是否已完成财务签约（status=1 且 finance_scope=1）
- `scope`: 用户授权范围
- `finance_scope`: 财务授权状态（1=已签约，0=未签约）
- `status`: 授权状态（1=有效，0=已撤销）
- `created_at`: 首次授权时间
- `authorized_at`: 财务授权时间

## 6. 服务端回调与签名安全

当异步任务（如扣款、撤销授权）完成时，Provider 会 `POST application/json` 到接入方。

### 6.1 扣款结果回调

当扣款完成（成功或失败）时，Provider 会向应用配置的回调地址发送通知。

**请求方法:** `POST`
**Content-Type:** `application/json`

**请求体示例:**
```json
{
  "appid": "app_xxx",
  "openid": "o_xxx",
  "order_no": "ORD123",
  "trade_no": "zod_xxx",
  "amount": 10.00,
  "status": "success",
  "balance": 90.50,
  "timestamp": 1704067200,
  "nonce": "random_str",
  "event_id": "evt_xxx",
  "sign2": "sha256_signature"
}
```

**字段说明:**
- `appid`: 应用标识
- `openid`: 用户 OpenID
- `order_no`: 外部订单号
- `trade_no`: 平台交易号
- `amount`: 扣款金额
- `status`: 扣款状态（`success`/`failed`）
- `balance`: 扣款后余额
- `timestamp`: Unix 时间戳
- `nonce`: 随机字符串
- `event_id`: 事件 ID（用于去重）
- `sign2`: 签名

**接入方应返回:**
```json
{
  "code": 0,
  "message": "success"
}
```

### 6.2 撤销授权回调

当用户撤销授权时，Provider 会向应用配置的回调地址发送通知。

**请求方法:** `POST`
**Content-Type:** `application/json`

**请求体示例:**
```json
{
  "appid": "app_xxx",
  "openid": "o_xxx",
  "user_id": 123,
  "finance_granted": 1,
  "status": "revoked",
  "revoked_at": 1704067200,
  "timestamp": 1704067200,
  "nonce": "random_str",
  "event_id": "evt_xxx",
  "sign2": "sha256_signature"
}
```

**字段说明:**
- `appid`: 应用标识
- `openid`: 用户 OpenID
- `user_id`: 用户 ID
- `finance_granted`: 财务授权状态（1=已授权，0=未授权）
- `status`: 状态（`revoked`）
- `revoked_at`: 撤销时间（Unix 时间戳）
- `timestamp`: Unix 时间戳
- `nonce`: 随机字符串
- `event_id`: 事件 ID（用于去重）
- `sign2`: 签名

**接入方应返回:**
```json
{
  "code": 0,
  "message": "success"
}
```

### 6.3 签名算法 (Sign2)
全链路仅支持 **V2 全字段签名**。算法如下：
1. 排除 `sign` 和 `sign2` 参数。
2. 将剩余所有参数按 Key 的 **ASCII 码升序排序**。
3. 将排序后的参数拼成 `key1=value1&key2=value2`（value 为数组或对象时转 JSON，字符进行 rawurlencode）。
4. 使用 `client_secret` 作为 Key，对该字符串执行 `HMAC-SHA256`。

### 6.4 幂等建议
回调 Payload 包含 `event_id`。接入方应：
1. **验签**: 验证 `sign2`。
2. **去重**: 检查 `event_id` 是否已处理过。
3. **处理**: 执行业务逻辑并返回 `200 OK`。

## 7. 错误码规范

| 错误码 | HTTP | 说明 |
| :--- | :--- | :--- |
| `invalid_request` | 400 | 参数缺失或格式错误 |
| `missing_token` | 401 | 缺少 `Authorization: Bearer <token>` 请求头 |
| `token_invalid` | 401 | `access_token` 无效、已吊销或已过期 |
| `invalid_client` | 401 | `client_secret` 校验失败 |
| `invalid_grant` | 400 | `code`/`refresh_token` 无效、已过期或触发家族重放吊销 |
| `unauthorized_client` | 403 | 应用不存在或未启用 |
| `not_authorized` | 403 | 用户未授权或已撤回应用授权 |
| `ip_not_allowed` | 403 | 调用 IP 不在白名单 |
| `deduct_failed` | 400 | 扣款失败（余额不足等） |

## 8. TG Bot 积分与身份互通端点

服务端鉴权接口（使用 `appid + appkey` 签名，无需用户 access_token）。

### 8.1 充值积分 (POST /points/add)
给指定用户充值站点积分（如 TG 社群签到领积分）。

**请求参数 (POST):**
- `appid`: 应用 ID (必须)
- `openid`: 用户 OpenID (必须)
- `amount`: 充值积分数量 (必须, 正整数, 单次不超过 10000)
- `desc`: 积分变动描述 (可选)
- `order_no`: 外部幂等流水号 (推荐, 传入后 30 天内自动防重, 重试不重复到账)
- `sign`: 签名 (必须)
  - 推荐: `sign = md5(appid + openid + amount + order_no + appkey)`
  - 兼容: `sign = md5(appid + openid + amount + appkey)`

**成功响应 (200 OK):**
```json
{
  "success": true,
  "user_id": 123,
  "amount": 10,
  "points": 120,
  "order_no": "CHECKIN_20261105_12345",
  "message": "积分充值成功"
}
```

**重复拦截响应 (200 OK, 幂等生效):**
```json
{
  "success": true,
  "user_id": 123,
  "amount": 10,
  "points": 120,
  "order_no": "CHECKIN_20261105_12345",
  "is_duplicate": true,
  "message": "重复请求已幂等拦截，积分已在此前完成充值"
}
```

### 8.2 查询积分余额 (GET /points/balance)
- `appid`, `openid`, `sign = md5(appid + openid + appkey)`

### 8.3 查询用户资料 (GET /user/profile)
- `appid`, `openid`, `sign = md5(appid + openid + appkey)`
- 返回 `display_name`, `invite_count` 等。

### 8.4 绑定 TG 用户 (POST /user/bindtg)
将 TG UID 与 WordPress 站点账号绑定（**具备强互斥检查，防抢绑与防多绑**）。
- 若 `tg_uid` 已被其他 WP 账号绑定，返回 `409 Conflict (tg_already_bound)`。
- 若 WP 账号已绑定其他 `tg_uid`，返回 `409 Conflict (user_already_bound)`。
- 参数: `appid`, `openid`, `tg_uid`, `tg_username`, `tg_display_name`, `sign = md5(appid + openid + tg_uid + appkey)`。

### 8.5 解绑 TG 用户 (POST /user/unbindtg)
- 参数: `appid`, `tg_uid`, `sign = md5(appid + tg_uid + appkey)`。
